# 11.8 其他网络子系统话题

以下几小节讨论网络子系统中几个不易归类的方面。

**带外数据**

处理带外数据的能力是流套接字抽象专有的设施。带外数据的语义应该是什么，看来共识甚少。TCP 定义了称为紧急数据（urgent data）的概念，把带内数据标记为 **紧急交付**；NBS 协议 [Burruss, 1980] 和许多其他协议提供一条完全独立的逻辑传输信道，用于发送带外数据。此外，一条带外消息可发送的数据量因协议而异，从 1 位到 16 字节或更多。

流套接字的带外数据概念定义为最低合理公约数。带外数据应脱离数据流的正常顺序和流控约束传输。支持流套接字的协议至少应提供 1 字节带外数据和一条未决带外消息。支持更大的消息或同时多条未决带外消息，是协议的权利。

带外数据由协议维护，通常不存放在套接字的接收队列。套接字级的 SO_OOBINLINE 选项用来在收到紧急数据时，强制把带外数据放进正常接收队列。把带外数据放进正常数据流，可以让协议同时保有多条带外消息。这一机制可以避免用户响应缓慢导致的带外消息丢失。

**地址解析协议**

地址解析协议（ARP）是链路级协议，为支持广播或多播通信的网络提供动态的地址翻译机制 [Plummer, 1982]。4.3BSD 用 ARP 把 32 位 Internet 地址映射为 48 位以太网地址。ARP 并非专用于 Internet 协议地址或以太网，但 4.3BSD 网络子系统只支持这一组合。ARP 并入网络接口层，尽管它逻辑上位于网络层与网络接口层 **之间**。

ARP 的基本想法简单：维护一张网络地址到链路级地址的翻译表。当网络接口向 ARP 服务发出地址翻译请求，而所请求的地址不在已知翻译表中时，ARP 创建一条报文，指明所请求的网络地址和一个未知的链路级地址。接口随即广播这条报文，期待网络上某台主机知道这个翻译——通常因为那台主机正是原消息的目的地。及时收到响应时，ARP 服务用该响应更新翻译表并解决未决的请求，随后调用请求的网络接口传输原消息。

实践中，这一算法的简单性因几方面要求而变得复杂：尽量减少名字翻译表和网络接口占用的资源、避免陈旧的翻译数据、处理失败的翻译请求。ARP 翻译表实现为一份翻译高速缓存：每个表项把一个 Internet 网络地址映射到相应的以太网地址，并关联一个定时器。表项组织成散列结构以加快查找。为外出消息把 Internet 地址解析为以太网地址的请求由这一调用发出：

```c
result = arpresolve(ac, m, destip, desten, usetrailers);
    struct arpcom *ac;
    struct mbuf *m;
    struct in_addr *destip;
    u_char *desten;
    int *usetrailers;
```

ARP 先查表看 Internet 地址 `destip` 是否已存在。地址已知且表项 **完整**（不在等响应）时，以太网地址从 `desten` 返回。如果地址没找到，ARP 必须在表中分配新表项、把外出消息排队待发、广播请求 Internet 地址翻译的报文；同时初始化表项的定时器，确保翻译请求若没有响应，存放该消息的 mbuf 链会被回收。若收到应答之前又有翻译请求到来，排队的那条消息被丢弃，只留较新的一条。

稍后——最好在排队消息的定时器到期之前——ARP 收到翻译请求的响应。收到的报文先由 `arpinput()` 例程处理（每个支持 ARP 的网络接口设备都调用它），再处理该 ARP 分组以定位翻译表项。报文完成了一次未决翻译时，表项更新，原消息交回网络接口传输；这一次对 `arpresolve()` 的调用将毫无延迟地成功。

ARP 的输入处理既要应对对本机地址的请求，也要应对本机发出的翻译请求的响应。输入模块还监视其他主机为本机 Internet 地址宣告翻译的响应。这种监视是为了确保同一网络上没有两台主机以为自己是同一个 Internet 地址（这一错误虽可检测，ARP 的对策也只是记一条诊断消息）。

ARP 通常在 20 分钟后让高速缓存中完成的翻译表项超时，3 分钟后让未完成的表项超时。表项可以标记为 **永久**（permanent），则永不从高速缓存删除；也可以标记为 **公布**（published），让一台主机充当不支持 ARP 的其他主机的代理。

ARP 对使用 Internet 协议的以太网络的顺畅运转很重要。但当不支持 ARP 的主机也在场时，它会带来兼容问题。公布表项可以用于不支持 ARP 的主机，但这些主机若不支持 Internet 地址与以太网地址之间完整的 32 位到 48 位映射，这就不足够。所幸多数 Internet 主机如今都支持 ARP。

**VAX UNIBUS 接口**

4.3BSD 支持的 VAX 硬件接口都驻留在 UNIBUS 上。UNIBUS 接口按主机与设备的通信走 DMA 还是走共享 UNIBUS 内存分为两类。支持 DMA 的设备使用一组处理 UNIBUS 的公共例程，其运作在此描述。

每个网络设备至少有收发消息各用的两个分组缓冲区。所有 DMA 传输都经 UNIBUS 适配器通往硬件设备所在的 UNIBUS。必须设置 UNIBUS I/O 映射寄存器，把 I/O 缓冲区的内存页映射进 UNIBUS 的地址空间（见图 11.10）。

![图 11.10 把消息从 VAX 地址空间映射到 UNIBUS 地址空间](../.gitbook/assets/fig-11-10-figure-11-10-mapping.png)

**图 11.10 把消息从 VAX 地址空间映射到 UNIBUS 地址空间**

每个 UNIBUS 接口利用一个 `if_ubinfo` 结构，装着设备在某个 UNIBUS 上各 I/O 缓冲区的总体信息。此外每个缓冲区有一个描述结构，含接口为把缓冲区映射进 UNIBUS I/O 空间所持有的 UNIBUS 资源。系统初始化时，为每个缓冲区分配足够的内存页和 UNIBUS 映射寄存器，把满尺寸的分组和头部完整映射进 UNIBUS 地址空间。缓冲区的 VAX 虚拟地址存在 `ifrw_addr`，映射寄存器从 `ifrw_mr` 开始。UNIBUS 映射寄存器 `ifrw_mr[-1]` 映射以页边界结尾的链路级协议头（为后述的尾部封装服务）。每个接收和发送缓冲区各关联附加结构——通常每接口各一。

发送消息时，接口软件必须把 mbuf 链的内容搬到一段在 UNIBUS 地址空间连续映射的内存。搬运靠复制数据完成，或者可能时设置 UNIBUS 适配器的映射寄存器，把 mbuf 持有的数据页映射进 UNIBUS 地址空间的适当区域。后一种情况，通常映射发送缓冲区各页的映射寄存器被暂时改为指向 mbuf 数据页；下次使用时恢复为引用发送缓冲区的保留页。内容被映射待传的 mbuf 排队等传输后释放；内容被复制的 mbuf 立即回收。

收到已传入 VAX 内存的消息时，必须做类似的过程。传输含至少半页数据时，从 mbuf 页池分配页框，与已含数据的页交换。新页映射进接收缓冲区替换刚放进 mbuf 的页，使设备为下一次 UNIBUS 传输就绪。

在复制内存的 CPU 开销高于重映射内存页开销的机器上，页的重映射可以改善网络性能。这种重映射只有在消息大到允许此类操作时才可能（最常见的是传输使用以太网等局域网时）。使用尾部封装也与这一方案配合良好，有可能让数据从设备输入到用户地址空间无须复制。

**尾部协议**

内存到内存的复制可以占网络数据传输服务开销的相当部分 [Watson & Mamrak, 1987]。因此设计者在网络软件的设计上花大力气把这类操作减到最少。许多体系结构提供按页组织的虚拟内存硬件，允许 I/O 传输按页映射。减少复制操作的一个诱人方案是把数据保持在页对齐边界上的页大小单元中，系统靠改页表项而不是物理复制来搬移数据。套接字软件尽量把用户数据放进带关联页的 mbuf（见 10.6 节）。支持 DMA 的 VAX UNIBUS 设备利用例程在可能时把页重映射进 UNIBUS 地址空间以备 DMA。这有可能让数据传输只经一次复制完成。在现行内存管理方案下，数据必须复制进内核地址空间；网络软件移植到的其他一些系统则不需要复制。

遗憾的是，从网络接收数据时做类似操作很困难。考虑入局分组的格式：分组典型地含一个链路级协议头，后跟更高层协议使用的一个或多个头，最后才是数据（若有）。头部信息长度可变，没有协议头格式的先验知识就无法保证送往用户接收缓冲区的数据在内存中正确对齐（例如系统只支持单一协议头格式时，头长就是已知的）。

为了既允许变长协议头存在、又保证数据的页对齐，可以使用一种特殊的本地网络封装。这一封装称为尾部协议（trailer protocol）[Leffler & Karels, 1984]，把变长头部信息放到数据之后（见图 11.11）。链路级头含一个新的尾部专有协议类型值，编码数据部分的大小；变长头部信息之前插入一个新的尾部协议头。尾部协议含原始分组类型和其后协议信息的大小。链路级协议头若定长（通常如此），输入 DMA 可以按该头的大小偏移，确保数据落在页对齐的内存区域。

![图 11.11 尾部协议的分组格式](../.gitbook/assets/fig-11-p339-trailer-protocol-packet-format.png)

**图 11.11 尾部协议的分组格式**

尾部协议的处理简单。输出时，链路级头中的分组类型设为指示使用尾部封装。类型从为尾部保留的一组类型中按尾部协议头之前的消息中的数据页数目选取。尾部协议头初始化为含实际分组标识和变长头部的大小，随变长头部信息一起附在数据之后。

输入时，接口例程凭链路级头中的分组类型识别尾部封装，计算数据页数以找到尾部的开头。尾部协议头信息复制进单独的 mbuf，链到所得分组的前端。数据部分留在接收缓冲区的页中，为接收缓冲区分配新页。

尾部协议需要源主机与目的主机合作。为了可以逐主机协商尾部，ARP 服务加入了尾部协议使用的协商。一对主机之间正常的 ARP 请求与响应报文交换期间，每台主机可以额外为尾部协议类型发一条 ARP 响应，表示愿意接收尾部封装的分组。

对驻留在以太网并使用 ARP 的网络接口，每次解析 Internet 地址的调用都返回接收主机是否愿意接收尾部协议的指示。只有主机表明愿意接收，系统才发送尾部封装。在不经 ARP 协商尾部的网络上，尾部封装的分组总是被接受；若网络上的主机无法接收尾部，可在接口结构中设置 IFF_NOTRAILERS 标志停用尾部。
