# 1.4 发布工程

CSRG 始终是一小群软件开发者。资源有限，要求谨慎的软件工程管理。需要细心协调的不仅是 CSRG 人员，还有为系统开发做贡献的社区成员。主要发行版通常在两类之间交替：

- 重大新设施：3BSD、4.0BSD、4.2BSD
- 错误修复与效率改进：4.1BSD、4.3BSD

这种交替既保证及时发布，又为新设施的精炼与纠错、以及消除新设施带来的性能问题留出余地。新设施发布之后及时跟进，反映出 CSRG 对提供一个可靠、健壮、用户社区可以信赖的系统何等重视。

CSRG 的开发成果分三步发布：alpha、beta 和 final，如表 1.1 所示。alpha 和 beta 版并不是真正的发行版——它们是测试系统。alpha 版通常只提供给少数站点，其中多数在校内。得到 beta 版的站点更多，但不直接获取；整个流程组织成树状，让错误报告、修复和新软件先由第一层站点收集、评估并查重，再转交 CSRG。例如，4.1aBSD 曾在 100 多个站点运行，但一级 beta 站点只有大约 15 个。这棵 beta 测试树让 CSRG 的开发者得以专注于实际开发，而不是在来自每个 beta 站点的细节里筛筛捡捡。本书的技术审校也经由类似的过程完成。

表 1.1 发布测试步骤

| | alpha | internal | beta | final |
| ---- | ---- | ---- | ---- | ---- |
| 名称 | 4.1aBSD | 4.1bBSD | 4.1cBSD | 4.2BSD |
| 主要新设施 | 联网 | 快速文件系统 | 进程间通信 | 修订后的信号 |

许多一级 beta 测试人员不仅在自己的机器上运行发行版，还在伯克利的开发机上拥有登录账号。这些用户常常从马萨诸塞、犹他、马里兰、得克萨斯、伊利诺伊这样远的地方，或斯坦福这样较近的地方，经由 ARPA Internet、有时通过电话拨号登录到伯克利。在 4.3BSD 发行期间，某些账号和用户有权直接修改系统源码的主副本。许多设施——如 Fortran 和 C 编译器，以及 `telnet` 和 `ftp` 等重要系统程序——都包含非 CSRG 人员的重大贡献。这一做法有一个重要例外：对内核的修改只能由 CSRG 人员进行，尽管修改常常出自更大社区的提议。

获准访问主源码的人事先经过仔细筛查，但并不受到严密监督。他们的工作在 beta 测试期结束时由 CSRG 人员检查——把上一版的源码与当前主源码做一次完整比较，例如把 4.3BSD 与 4.2BSD 相比。被认定不合适的设施，例如目录列表命令的新选项或 `fseek()` 库例程返回值的变更，会在最终发行前从源码中剔除。

4BSD 发行版通常附带一对文档，逐一说明每个用户级命令 [McKusick et al., 1986] 和每个内核源文件 [Karels, 1986] 的变化。这些文档随最终发行版交付。用户按名字一查任何命令，就能立即看到改了什么；开发者同样可以按名字查任何内核文件，得到该文件变化的摘要。

这个过程展示了 **主力开发者人数少** 的一个优点：所有开发者都透彻了解整个系统，足以把自己的工作与他人的工作协调起来，产出连贯一致的最终系统。拥有庞大开发组织的公司发现这种结果难以复制。

CSRG 没有市场部门。因此，技术决策基本出于技术理由，不受营销承诺驱使。伯克利的开发者对此近乎偏执，并以从不承诺具体交付日期而闻名。
